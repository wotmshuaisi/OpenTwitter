# Feature Specs

Each spec lists scope, out-of-scope, and acceptance criteria — kept small and literal so each can be a single implementation task for a small model.

## 1. User registration & login
**Scope**: `/register` (username, email, password → `bcrypt.hash`), `/login` (session cookie via `express-session`), `/logout`. Simple server-rendered forms, no client JS required, htmx only for inline validation errors if desired.
**Out of scope**: OAuth/social login, 2FA, email verification (can be added later — flag to confirm).
**Acceptance**: duplicate username/email rejected with a clear form error; passwords never stored in plain text; login rate-limited (simple in-memory counter per IP is enough at this scale).

## 2. Follow / follower system
**Scope**: follow/unfollow button on profile page as an `hx-post`/`hx-delete` that swaps just the button's HTML fragment; follower/following counts on profile; `/u/:username/followers` and `/u/:username/following` list pages.
**Acceptance**: self-follow blocked server-side; duplicate follow blocked by the `UNIQUE(follower_id, following_id)` constraint (catch the SQLite constraint error and show a friendly no-op).

## 3. Post creation with image and video support
**Scope**: composer form (`multer` for multipart upload) — text (280 char limit) + optional single image or video. On submit, insert `post` row, insert `media` row with `status='pending'`, enqueue `generateThumbnail` (image) or `transcodeVideo` (video) job, return the new post-card fragment via htmx with a "processing…" placeholder over the media area.
**Acceptance**: post appears in the timeline immediately; once the job completes, the socket.io `media:ready` event triggers an htmx `hx-get` refresh of that one post card so the real media replaces the placeholder without a full page reload.

## 4. Mentions, reposts, and sharing
**Scope**:
- **Mentions**: on post save, regex-scan `body` for `@username`, look up matching users, insert `mentions` rows, render `@username` as a link in the template.
- **Repost**: `hx-post /posts/:id/repost` inserts a `posts` row with `type='repost'`, `repost_of_id` set, `body=NULL`; shows "Reposted by X" above the original post card in feeds.
- **Quote post**: small composer variant that also sets `repost_of_id` but keeps `type='quote'` and a non-null `body`; template renders the quoted post as a nested card.
- **Sharing**: a plain "Copy link" button using the browser's built-in clipboard API (a few lines of inline JS, no library needed) that copies the post's permalink.
**Acceptance**: reposting twice by the same user is a no-op (unrepost instead); quote posts render the original inline; copy-link shows a brief "Copied!" confirmation.

## 5. Analytics and statistics
**Scope**: record `post_view` / `profile_view` events (fire-and-forget insert into `analytics_events` on page load — cheap enough at this scale to do inline rather than queued, but batched via a single prepared statement); a scheduled rollup (`setInterval` once per hour, or a cron-style call in `jobs/handlers/rollupAnalytics.js`) aggregates `analytics_events` into `analytics_daily_rollups`; `/dashboard` page reads only from the rollup table and renders simple `<canvas>` bar/line charts using a tiny vendored charting script (or plain SVG — no charting library dependency needed for a handful of bars).
**Acceptance**: dashboard loads fast because it never scans raw events at request time; own-content-only (a user sees their own stats, not others').

## 6. Direct messaging
**Scope**: 1:1 conversations only (group DMs out of scope for v1). Conversation list page, thread view, `hx-post` to send a message (returns the new message bubble fragment), Socket.io for live delivery to the recipient if they have the thread open, unread badge based on `last_read_message_id`.
**Acceptance**: messages persist even if the recipient is offline (they see them on next load via the normal DB query); read marker updates when a thread is opened; single optional media attachment per message reuses the same storage/media pipeline as posts.

## 7. User profiles
**Scope**: avatar + header image upload (reuses storage/media pipeline), display name, username, bio, location, website, joined date, grid/list of the user's posts, follower/following counts, `/settings/profile` edit form.
**Acceptance**: profile page renders under 1.5s on a warm SQLite cache; uploads go through `storage.put()`; profiles are public by default (no privacy settings requested).

## Explicitly deferred — confirm with you before building
- Likes/favorites (spec mentions reposts/sharing, not likes)
- Group DMs
- Email verification / password reset flow
- Notifications center UI (DB rows for mentions/follows can still be written now, surfaced later)
- Content moderation/reporting tools
- Public API for third-party/mobile clients
