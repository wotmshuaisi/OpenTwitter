# Non-Functional Requirements

## Performance
- No bundler/build step means very little client-side JS weight by default — keep it that way; avoid adding npm frontend packages "just in case."
- Target sub-1.5s page load: server-rendered HTML + htmx swaps are inherently fast; the main risk is unindexed SQL queries, so every list/lookup query in `db/*.js` should hit an index (see schema doc).
- Images served via `sharp`-generated resized variants, not the original upload, for feed thumbnails.
- Video: serve the ffmpeg-generated poster/thumbnail by default; only load the full video on click/play.

## SQLite specifics
- WAL journal mode, `busy_timeout` set, single Node process (no multi-process cluster mode for the DB writer, to avoid `SQLITE_BUSY` complexity — if scaling is needed later, revisit).
- `better-sqlite3` is synchronous — keep queries fast and simple (indexed lookups) so they never block the event loop noticeably; anything heavier (analytics rollups, media processing) goes through the `jobs` table instead of running inline.
- Periodic `VACUUM` (e.g. weekly, via the same `setInterval`-style scheduler used for job polling).

## Security
- `bcrypt` for password hashing (10-12 rounds).
- `express-session` with `httpOnly`, `sameSite=lax` cookies; session store backed by the same SQLite DB (one dependency, not a separate Redis store).
- CSRF: since forms are same-origin and htmx sends normal POST requests, use a small CSRF-token-in-hidden-field pattern (`csurf` or a hand-rolled token check) on state-changing routes.
- File uploads: validate MIME type via `sharp`/`fluent-ffmpeg` actually opening the file (not just trusting the extension), enforce size limits in `multer` config, strip EXIF on image resize (sharp does this by default when re-encoding).
- Never build `storage_key` paths from user-supplied filenames directly — always generate them server-side (see storage abstraction doc) to avoid path traversal.
- Basic per-IP rate limiting on `/login` and `/register` (a small in-memory counter is sufficient at this scale — no external rate-limit service needed).

## Accessibility
- Semantic HTML first (real `<button>`/`<a>` elements, not `<div onclick>`), since htmx works directly on real elements.
- `aria-label` on icon-only controls (follow, repost, share, send).
- Visible focus states in `base.css`.
- Respect `prefers-reduced-motion` for any CSS transitions.

## Testing
- Keep it lightweight to match the stack: `node:test` (built into Node, no extra dependency) or `tap` for `db/*.js` function tests (these are plain functions against a temp SQLite file — easy to test in isolation).
- A handful of `supertest`-based route tests for the critical flows: register → login → post → follow → DM.
- Storage abstraction: run the same small test suite against `storage/local-disk.js` pointed at a temp dir; re-run against `storage/s3-compatible.js` (with a local MinIO container) once that driver exists, to confirm parity before any real migration.

## Observability
- Plain `console.log`/`console.error` with a consistent prefix (e.g. `[job:generateThumbnail]`) is enough at this scale — no logging framework needed initially.
- Failed jobs stay in the `jobs` table with `status='failed'` and an `attempts` count — visible via a simple `SELECT * FROM jobs WHERE status='failed'` for now; a small `/admin/jobs` debug page can be added later if useful.
- A `/health` route returning `200 OK` for basic uptime checks.
