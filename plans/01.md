# Project Plan — Twitter-like Social Platform (Lightweight Stack)

## Why this stack

The implementation model (Qwen3.5-4B-class) is small — it works best with **explicit, boring code** and as few abstraction layers as possible. Every choice below optimizes for "the model can hold the whole pattern in its head at once," not for enterprise scale.

## Stack

- **Runtime**: Node.js (LTS), plain **JavaScript** (no TypeScript — one less compiler/type layer for the model to reason about)
- **Web framework**: **Express** — minimal, unopinionated, every route is `app.get('/path', handler)`. No decorators, no DI container, no CLI code generators.
- **DB**: **SQLite** via `better-sqlite3` — synchronous API (no async/await needed for queries), so query code reads top-to-bottom with no callback/promise indirection. Raw SQL in plain strings, small hand-written query functions, **no ORM**. A tiny `db/` folder of query functions is easier for a small model to extend correctly than an ORM's query builder DSL.
- **Templates**: **EJS** (`<%= %>` / `<% %>`) — plain HTML with embedded JS, no new template language to learn, renders server-side.
- **Frontend interactivity**: **htmx** only (one `<script src="htmx.js">` tag, no npm frontend deps, no bundler/build step, no JSX). Interactions are `hx-get` / `hx-post` / `hx-target` attributes on plain HTML — the model edits HTML attributes, not JavaScript logic, for most UI behavior.
- **Real-time (DMs, notifications)**: **Socket.io** — one of the most common, best-documented real-time libraries; a small model can reliably generate the emit/on pairs.
- **Sessions/auth**: `express-session` (SQLite-backed session store) + `bcrypt` for password hashing. No Passport.js strategy config — one straightforward login route.
- **File storage**: local filesystem via Node's `fs` module, wrapped in a tiny pluggable module (see `03-storage-abstraction.md`) — a plain object with `put/get/url/delete` functions, not a class hierarchy.
- **Image/video processing**: `sharp` (images) + `fluent-ffmpeg` wrapping the system `ffmpeg` binary (video thumbnail + basic transcode). Both are extremely common in training data.
- **Background jobs**: no external queue system (no Redis/BullMQ). A `jobs` SQLite table + a `setInterval` poller in the same Node process. This keeps the whole app to one process and one dependency (SQLite) — much easier for a small model to reason about than a second service.
- **CSS**: plain CSS file(s), no Tailwind build pipeline, no PostCSS.

## What we deliberately avoid, and why

| Avoided | Reason |
|---|---|
| Laravel / any MVC framework | Convention-heavy "magic" (service containers, facades, artisan generators) — hard for a small model to predict correctly |
| Livewire / FluxUI | Requires knowing a large proprietary component API + tight PHP/JS request-lifecycle coupling |
| React/Vue/Svelte + bundler | Build step, JSX syntax, client state management, npm dependency graph — many places for a small model to introduce broken imports |
| TypeScript | Extra type-checking layer; plain JS reduces syntax errors from a small model |
| ORM (Prisma/Sequelize/TypeORM) | Query builder and migration DSLs are their own mini-language to get wrong; raw SQL is more literal and predictable |
| Redis / BullMQ / message brokers | Second service to run and configure; SQLite-backed job table is "good enough" at this scale and keeps deployment to one process |
| Three.js / heavy animation libraries | Explicitly dropped per "lightweight" direction — see note below |

**Note on the previous "premium" direction**: given the lightweight constraint and a small implementation model, we are **not** pursuing WebGL/Three.js effects, magnetic-cursor effects, or heavy glass-morphism theming in the initial build. Polish (dark/light theme toggle, clean typography, simple CSS transitions) stays in scope; anything requiring hand-tuned animation JS is deferred until the core product works.

## Guiding principles for a small implementation model

1. **One file, one job.** Prefer many small files (`routes/posts.js`, `db/posts.js`, `views/posts/show.ejs`) over few large ones — smaller context per edit, less chance of losing track.
2. **No hidden control flow.** Every route explicitly queries the DB and renders a template — no middleware pipeline the model has to trace to understand "where did this data come from."
3. **Copy-paste-friendly patterns.** Once one CRUD route (e.g. posts) is written well, reuse the same shape for the next (e.g. messages) — consistency over cleverness.
4. **htmx over client JS.** Any interaction that can be `hx-post` + a server-rendered HTML fragment response should be — avoids the model writing client-side state bugs.
5. **SQLite-aware, single process.** WAL mode, synchronous `better-sqlite3` calls, no separate services beyond the one Node process.

## High-level roadmap

```
Phase 0  Project scaffolding (Express + EJS + htmx + SQLite wiring)
Phase 1  Auth, sessions, profiles, follow system
Phase 2  Storage abstraction + media pipeline (sharp/ffmpeg + jobs table)
Phase 3  Posts (text/image/video), mentions, reposts, sharing
Phase 4  Feed, timeline, search (SQLite FTS5)
Phase 5  Direct messaging (Socket.io)
Phase 6  Analytics & statistics
Phase 7  UI polish pass (theme toggle, spacing, simple transitions — no WebGL)
Phase 8  Performance hardening, accessibility, QA, deployment prep
```
