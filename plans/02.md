# Architecture

## Folder structure (flat, explicit, small files)

```
app.js                      # Express app setup, middleware, session, route mounting
server.js                   # http server bootstrap + socket.io attach + job poller start

db/
  connection.js              # opens SQLite file, sets pragmas (WAL, foreign_keys)
  schema.sql                 # all CREATE TABLE statements, run once on startup if missing
  users.js                   # plain functions: createUser(), findByUsername(), ...
  follows.js                 # followUser(), unfollowUser(), listFollowers(), ...
  posts.js                   # createPost(), getTimeline(), getPostById(), ...
  mentions.js
  media.js
  messages.js
  conversations.js
  analytics.js
  jobs.js                    # enqueueJob(), claimNextJob(), markJobDone()

storage/
  index.js                   # pluggable storage module (see 03-storage-abstraction.md)
  local-disk.js               # local filesystem driver
  s3-compatible.js             # (added later) S3-compatible driver, same function shape

media/
  images.js                   # sharp-based resize/thumbnail functions
  video.js                     # fluent-ffmpeg based thumbnail/transcode functions

jobs/
  worker.js                    # setInterval poller, dispatches to job handlers below
  handlers/
    generateThumbnail.js
    transcodeVideo.js
    rollupAnalytics.js

routes/
  auth.js                      # /register, /login, /logout
  profiles.js                  # /u/:username, /settings/profile
  follows.js                   # /u/:username/follow, /unfollow (htmx endpoints)
  posts.js                     # /posts, /posts/:id, /posts/:id/repost, /posts/:id/quote
  feed.js                       # / (home timeline), /search
  messages.js                   # /messages, /messages/:conversationId
  analytics.js                  # /dashboard

middleware/
  requireAuth.js               # redirect to /login if no session user
  currentUser.js                # attaches req.user from session for every request

views/                          # EJS templates, one subfolder per route group
  layout.ejs
  partials/
    nav.ejs
    post-card.ejs               # reused fragment, also returned directly by htmx endpoints
    theme-toggle.ejs
  auth/
  profiles/
  posts/
  feed/
  messages/
  analytics/

public/
  htmx.min.js                   # vendored, no npm frontend build
  css/
    base.css
    theme.css                   # light/dark/system variables

media-storage/                  # local disk root, gitignored (matches storage abstraction's "local" driver)
```

## Request lifecycle (example: creating a text+image post)

1. Browser submits `hx-post="/posts"` from the composer partial (multipart form with file input).
2. `routes/posts.js` handler: validates body text length, checks `req.file` (via `multer` middleware) exists.
3. Handler calls `db/posts.js -> createPost()` (plain SQL insert, returns new row synchronously — `better-sqlite3` is sync).
4. If a file was uploaded, handler calls `storage.put()` (see storage abstraction) to move it into permanent storage, then `db/media.js -> attachMedia()` to link it to the post with `status = 'processing'`.
5. Handler calls `db/jobs.js -> enqueueJob('generateThumbnail', { mediaId })`.
6. Handler renders the `partials/post-card.ejs` fragment for the new post and returns it directly (htmx swaps it into the timeline) — no client-side JS needed.
7. The job poller (`jobs/worker.js`, already running via `setInterval` in `server.js`) picks up the queued job within its poll interval (e.g. every 2s), runs `generateThumbnail.js`, updates the media row's `status` to `ready`, and (for pages currently open) emits a socket.io event `media:ready` so the open tab can htmx-refresh that one post card.

## Module boundaries & rules

- **Routes never write raw SQL.** They call functions from `db/*.js`. This is the one abstraction we keep, because it means route files stay short and the SQL lives in one predictable place per entity.
- **Routes never touch `fs` directly.** They call `storage.put/get/url/delete` from `storage/index.js`. This is the pluggability boundary described in `03-storage-abstraction.md`.
- **No class hierarchies.** Everything is plain functions and plain objects (`module.exports = { put, get, ... }`). A small model handles "call this function" far more reliably than "extend this abstract class."
- **Views only receive data, never query the DB themselves.** Route handlers fetch everything the template needs and pass it in `res.render('posts/show', { post, author, mediaList })`.

## Real-time updates

- **Socket.io**, attached to the same HTTP server in `server.js`.
- Rooms: `user:{id}` (personal notifications, DM delivery), `post:{id}` (media-ready updates for viewers currently looking at that post).
- Client-side: a single small `<script>` block (inline in `layout.ejs`, ~20 lines) that joins the current user's room and, on relevant events, triggers an `htmx.trigger()` / `hx-get` refresh of the affected DOM element — no client state management framework needed.

## Background jobs (SQLite-backed, no Redis)

```sql
CREATE TABLE jobs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  type TEXT NOT NULL,
  payload TEXT NOT NULL,       -- JSON string
  status TEXT NOT NULL DEFAULT 'pending', -- pending | processing | done | failed
  attempts INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```
`jobs/worker.js` polls every few seconds with `SELECT ... WHERE status = 'pending' LIMIT 5`, marks each `processing`, dispatches to the matching handler in `jobs/handlers/`, and marks `done`/`failed` with a simple retry count. This is intentionally the simplest possible durable queue — one table, one poller function, no new service.
